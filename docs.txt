CHANGE code-driven technical reference

This document is written from inspection of the current source tree, especially `c/`, and describes the system as implemented.

1. System intent from the code

The project is a native C backend that keeps three interdependent runtime models:

- a semantic graph of user-related concepts
- a goal graph with hierarchy and execution order
- a derived schedule built from goal progression

Those models are then queried and manipulated by a constrained AI-driven research loop called deep search.

The code does not implement a general chatbot. The AI calls are inserted at specific transformation points:

- turning free text into graph updates
- choosing investigative commands during deep search
- judging whether an investigation conclusion is strong enough
- turning a research result into a normalized goal
- decomposing a goal into subgoals
- rewriting a failing goal into a shorter variant

The architecture is therefore:

- deterministic in-memory state engine in C
- LLM-assisted semantic transforms at boundaries
- HTTP and SSE wrapper around the engine
- two separate browser/mobile-facing UIs around that wrapper


2. Top-level layout

Relevant top-level directories and files:

- `c/`
  Core engine, server, CLI entrypoint, support libraries.
- `js/`

3. Process entrypoint and ownership model

`c/main.c` is intentionally small:

- `UIStart()`
- `UILoop()`
- `UIKill()`

The real bootstrap lives in `c/cli/ui.c`.

`UIStart()` does the following:

1. `InitNodes()`
2. `SetUpContexts()`
3. `InitGlobalPointerMap()`
4. registers `ds_emit`
5. registers `goal_emit`
6. `InitGoalSystem()`

This matters because the application is built around one shared process state, not around isolated instances.

The graph, goal container, schedule cache, and callback registry are all global.


4. Meaning of `c/`

`c/` is the actual product.

Subtree responsibilities:

- `c/ne/`
  Main domain logic. "ne" is the neuro engine area.
- `c/srv/`
  Network wrapper around the engine.
- `c/lib/`
  Internal support libraries.
- `c/cli/`
  Local terminal shell for manual operation.
- `c/config.h`
  Prompt templates, ports, file paths, and formula constants.
- `c/globals.*`
  Runtime registry for callback pointers shared across modules.

The `js/` and `react/` directories are wrappers around this C backend, not peers in system ownership.


5. The neuro engine: what it is in this repository

The neuro engine is not a neural-network inference module.

By reading `c/ne/`, it is better described as a semantic memory and investigation engine with these parts:

- graph storage
- graph activation and weight dynamics
- semantic import from user text
- search operators over graph structure
- deep-search orchestration
- goal and schedule subsystems integrated into the same evidence space

The engine's "neuro" aspect comes from:

- spreading importance through connections
- temporal activation decay
- contextual weighting through parent chains
- reinforcement from repeated search usage

It is a symbolic/heuristic engine, not a numeric model trainer.


6. Fixed graph contexts

The graph always begins with five top-level nodes declared in `c/ne/node.h`:

- `profesie`
- `emotie`
- `pasiuni`
- `generalitati`
- `subiectiv`

`SetUpContexts()` in `c/cli/ui.c` materializes them at process startup and stores their indexes in the global `Contexts[]` array.

These roots are not metadata tags. They are real graph nodes, and every imported concept is expected to live under one of them.


7. Graph storage model

7.1. Global node container

Defined in `c/ne/node.h`:

- `Nodes.items`
- `Nodes.capacity`
- `Nodes.count`
- `Nodes.needsRefresh`
- `Nodes.init`

This is the central memory store for all identity graph nodes.

7.2. `Node`

Fields of `Node`:

- `label`
- `hasParent`
- `labelLength`
- `_weight`
- `_activation`
- `neighbours`
- `nsize`
- `ncount`
- `globalIndex`
- `lastTouched`
- `pendingTouches`
- `times_seen`
- `times_used`
- `parent`
- `childrenIndex`

Operational meaning:

- `_activation`
  Local current salience before parent scaling.
- `_weight`
  Local long-term importance before parent scaling.
- `pendingTouches`
  Deferred salience increments waiting to be applied.
- `times_seen`
  Search exposure count.
- `times_used`
  Search anchor count.
- `childrenIndex`
  Fast child lookup table keyed by lowercase label.

7.3. `Connection`

Fields of `Connection`:

- `_activation`
- `_weight`
- `lastTouched`
- `pendingTouches`
- `target`

Connections are adjacency-list entries stored inside each source node.

7.4. Global connection count

`ConnectionCount` is a global count used mainly for graph export sizing.


8. Node creation and indexing

`AddNodeEx(...)` in `c/ne/node.c` performs:

- lowercase normalization
- global container growth if needed
- adjacency allocation
- optional registration under parent `childrenIndex`
- optional allocation of a child dictionary if the node is marked fertile

The contexts are created as fertile roots. Most imported semantic nodes are added as infertile leaves in the current input pipeline.

Two lookup paths exist:

- `FindNode(...)`
  Child lookup under a known parent via hash dictionary.
- `FindNodeGlobal(...)`
  Linear label search through the global node array.

`FindNodeGlobal(..., CONTEXT_COUNT)` is how context roots are recovered during import.


9. Effective score reading

The stored fields `_activation` and `_weight` are not the only values used at runtime.

The functions:

- `read_node_activation`
- `read_node_weight`
- `read_connection_activation`
- `read_connection_weight`

walk upward through parent links and multiply values along the chain.

Result:

- a node's effective value depends on its own local state and its context ancestors
- a connection's effective value depends on its own local state and the target's ancestry

This makes contexts active scaling layers rather than passive categories.


10. Text ingestion pipeline

Entry function:

- `DecomposeInputIntoGraph(String *input)`

Implementation path:

1. build a prompt using `DECOMPOSITION_INTO_GRAPH_PROMPT`
2. call OpenAI Responses API with strict schema `OPENAI_DECOMPOSITION_SCHEMA_JSON`
3. parse the API JSON response
4. extract output text from the nested `output -> content -> text` structure
5. parse that text as JSON again
6. send each top-level context object to `AddContextNodesFromJSON(...)`

The AI is therefore used as a structured semantic extractor.


11. Graph import semantics

`c/ne/input/json-to-graph.c` converts schema output into graph mutations.

11.1. Node import

For every node object inside a context:

- read `name`
- optionally read `activation`
- optionally read `weight`

If the node already exists under the context root:

- `touch_node(existing, activation, now)`

If not:

- create the node with default activation
- blend the imported weight with `NODE_GUESS_WEIGHT_RELEVANCE`

11.2. Connection import

For every connection object:

- read `nodes`
- read optional `activation`
- read optional `weight`
- resolve both endpoint labels inside the same context

If a link already exists:

- `touch_connection(existing, activation, now)`

If not:

- create bidirectional links
- add a small activation bonus
- blend imported weight with `CONNECTION_GUESS_WEIGHT_RELEVANCE`

11.3. Identity consequence

Imported graph state is cumulative and contextual:

- repeated concepts do not duplicate inside the same context
- repeated links do not duplicate
- the AI influences initial structure but cannot fully dictate long-term importance


12. Deferred touch model

Both nodes and connections use deferred updates.

`touch_node`:

- sets `lastTouched`
- adds `log1p(power)` to `pendingTouches`

`touch_connection` does the same for edges.

This means ingestion and search do not fully recompute activation immediately. They queue influence that gets folded in during graph refresh.


13. Graph refresh and weighting

`RefreshGraph()` in `c/ne/graph/graph-engine.c` is the main update pass.

It performs two jobs:

- refresh activation with time decay and pending touches
- recompute node weights from usage and structural support

13.1. Time decay

Decay formula uses:

- `ACT_HALFTIME`

through:

- `value * pow(2.0, -dt / ACT_HALFTIME)`

This is used for activation, not for stored weight.

13.2. Support computation

For each node:

- every outgoing connection is refreshed
- connection contribution is `read_connection_weight + k * read_connection_activation`
- total support is divided by `1 + c * ncount`

where:

- `k = ACTIVATION_IMPORTANCE_TO_NODE_WEIGHT`
- `c = NCOUNT_PENALTY_TO_NODE_WEIGHT`

13.3. Usage normalization

The pass also finds maxima for:

- `times_seen`
- `times_used`
- support

Then normalizes each node against those maxima using `log1p`.

13.4. Weight update

The target weight is derived from:

- confidence = normalized `times_seen`
- merit = blend of support and `times_used`

Then:

- `new_weight = old_weight * NODE_OLD_WEIGHT_RELEVANCE + target * (1 - NODE_OLD_WEIGHT_RELEVANCE)`

This gives the graph a memory of search usage and topological reinforcement.


14. Search operators

The base search code is in `c/ne/search/search.c`.

14.1. Top-percent strategy

The search layer uses a generic quickselect-based function `FilterTopPercent(...)`.

It:

- computes the threshold corresponding to a percentage
- returns all entries scoring at least that threshold

This is used for:

- global node filtering by activation
- global node filtering by weight
- local neighbor filtering by activation
- local neighbor filtering by weight

14.2. Recursive neighborhood exploration

`ComputeNodeFamily(...)` recursively expands from a node up to `MAX_FAMILY_DEPTH`.

At every depth it filters outgoing edges by:

- activation percentage threshold
- weight percentage threshold

and serializes the reachable structure.

14.3. Search mutates learning signals

When nodes are exposed in search results:

- `times_seen` increases

When a node is used as the origin of a search:

- `times_used` increases

Search is therefore part of the learning loop, not a read-only query layer.


15. Deep-search engine

The deep-search loop is the most important orchestration layer around graph and goals.

Main files:

- `c/ne/search/deep-search-session.c`
- `c/ne/search/deep-search-execute.c`
- `c/ne/search/command-parsing.c`
- `c/ne/search/ai-action.c`

15.1. Session memory

Each session keeps:

- `persistent`
- `dynamic`

Persistent memory contains the long operating prompt and the task text.
Dynamic memory accumulates model outputs and runtime command results.

15.2. Prompt model

`DS_PERSISTENT_PROMPT` in `c/config.h` describes:

- the identity graph
- the goal system
- the schedule system
- the allowed commands
- the requirement to emit exactly one strict JSON action at a time

The model is explicitly told to investigate, not solve the user request directly.

15.3. Execution loop

`start_ds_session(...)` does:

1. build persistent prompt
2. emit `p-mem`
3. `RefreshGraph()`
4. emit `ds-start`
5. run internal rounds until model finishes
6. judge the conclusion
7. retry externally if judge rejects
8. emit final memories and `ds-end`

15.4. Actor/judge split

Deep search uses two separate AI roles:

- actor:
  chooses commands or produces a conclusion
- judge:
  validates whether the conclusion is sufficiently strong

If the judge fails:

- failure reason is appended into persistent memory as feedback
- dynamic memory is cleared
- the actor retries

15.5. Minimum depth guard

Each `Task` has `minDepth`.

If the model tries to finish before the internal round count reaches that minimum:

- completion is rejected
- feedback is appended to memory

This enforces a minimum evidence depth.


16. Deep-search command surface

Commands are validated in `command-parsing.c` and executed in `ai-action.c`.

Implemented commands:

1. global graph filtering
2. local graph neighbor search
3. recursive graph exploration
4. global goal evidence inspection
5. goal decomposition inspection
6. relational goal evidence inspection
7. schedule availability inspection

This command surface is how the neuro engine touches the goal engine.

Commands 1-3 query semantic identity state.
Commands 4-6 query behavioral goal state.
Command 7 queries time projection state.


17. Goal container model

Goal storage is implemented with:

- `Goal *GOAL_CONTAINER[1024]`
- `size_t GOAL_CONTAINER_COUNT`

index `0` is reserved, with:

- `INITIAL_GOAL_INDEX == 1`

Every goal carries both a stable string ID and a numeric `globalIndex`.

19. How goals are linked

This section answers the core structural question directly.

19.1. Parent-child links

Hierarchy is represented by:

- parent stores child indexes in `subgoals[]`
- child stores `parent = parentIndex`

This gives a decomposition tree.

19.2. Sequential links

Execution order between sibling-like tasks is represented by:

- `prev`
- `next`

The helper `link_goals(a, b)` sets those two fields symmetrically.

19.3. Why both are needed

The tree alone cannot express intended order.
The `prev/next` chain alone cannot express decomposition ownership.

This codebase uses both:

- tree for structure and recursion
- chain for progression and scheduling

19.4. Recursive time aggregation

`CalcGoalRequiredTime(g)`:

- returns leaf `required_time` directly
- or sums recursive child times plus `pauseToNext`

So parent duration is not independent. It is a derived total over its children chain.

19.5. Traversal helpers

The code implements several structural traversals:

- root lookup through repeated `parent`
- first leaf of a branch
- last leaf of a branch
- previous timeline leaf
- next leaf across sibling and parent boundaries

Those helpers are what make the mixed tree/chain representation usable.


20. Goal creation

`CreateUserGoal(...)` in `c/ne/goal/goal.c` is not a simple constructor.

Flow:

1. generate goal ID
2. build a deep-search task from user title + rationale
3. run personalized deep search
4. emit deep-search recommendation over goal SSE channel
5. extract normalized goal JSON from the research result using OpenAI
6. validate title, extra info, and estimated time
7. retry extraction if necessary with feedback
8. create the root goal
9. emit title, extra-info, and time
10. partially decompose the result

This means goals are born out of an AI-mediated interpretation layer, not directly from raw user text.


21. Goal decomposition

`DecomposeGoal(g)` creates subgoals for a large leaf goal.

21.1. Preconditions

Decomposition is skipped if:

- goal already has children
- goal required time is below `GOAL_MIN_SECONDS`

21.2. Context gathering

`SetGoalDecompositionPrompt(...)` builds a decomposition prompt using:

- recent user goal history
- same-layer siblings
- parent chain
- linked siblings
- parent siblings ("uncles")
- a fresh deep-search personalization context

This is an important system design point:

goal decomposition is not local to the goal text. It is conditioned on behavioral context and on deep-search interpretation.

21.3. AI result contract

The expected subgoal fields are:

- `title`
- `extrainfo`
- `estimated_time`
- `min_pause_to_next`
- `pause_to_next`

21.4. Materialization

For each returned subgoal:

- create a child goal
- assign `parent`
- assign generated goal ID
- assign pause constraints
- link it to the previous child using `link_goals`

At the end:

- parent `subgoals[]` is filled
- parent `subgoals_len` is set
- parent `required_time` is recalculated recursively

So decomposition produces both structural and sequential connectivity.


22. Goal progression logic

22.1. Starting a goal

`StartGoalDeepFromGoal(...)` does not simply start the passed goal.

Instead it finds the first unstarted executable leaf under that branch:

- recurse into first unstarted child leaf if needed
- ensure earlier timeline leaves are finished
- set `start_date`

This is why `/goal/start` can be invoked on a parent-like item but still start a deeper leaf.

22.2. Ending a goal

`EndGoalFromGoal(...)`:

- sets `end_date`
- marks `SCHEDULE_NEEDS_REFRESH = 1`

22.3. Session goals

`GetSessionGoals(...)` returns one current startable leaf per root branch.

This is effectively the backend's "current actionable work" view.


23. Goal validation and repair

23.1. Validation

`ValidateGoal(...)` currently only invalidates leaf goals that overrun their allowed duration.

Condition:

- started
- not ended
- elapsed time exceeds required time plus margin

23.2. Repair strategy

If invalid:

- for limited retries, extend required time by 25%
- after retry limit, ask AI to shorten/rewrite the goal

The goal rewrite appends an audit note into `extra_info`.

This shows that the goal system is designed to be adaptive under failure, not immutable.


24. Schedule subsystem

Main files:

- `c/ne/goal/user-schedule.c`
- `c/ne/goal/user-schedule.h`

24.1. Nature of schedule

The schedule is not user-entered calendar data.

It is a computed projection from:

- started goals
- finished goals
- `prev/next` ordering
- pause durations

24.2. Seed set

`GetLeafDueGoals(...)` identifies leaves that define the active frontier, such as:

- a started unfinished goal
- a finished goal whose immediate next goal exists but has not started

24.3. Refresh algorithm

`RefreshSchedule()`:

1. clears previous table
2. gathers due leaves
3. walks forward with `next_leaf(...)`
4. calculates event start times
5. writes `ScheduleEntry { time, goalIndex }`

If a goal has no explicit `start_date`, the projected start time is derived from:

- previous goal end time
- plus previous goal pause

24.4. Reporting

`SerializeScheduleData(...)` returns:

- threshold-relative report header
- rough work volume summaries
- detailed scheduled goal entries

This is predictive schedule output, not a durable scheduling database.


25. HTTP server as the wrapper around the engine

`c/srv/http-server.c` is the application shell that exposes the C engine to clients.

25.1. Server responsibilities

- parse HTTP requests manually
- manage SSE clients
- route graph, research, goal, schedule, and dev-time endpoints
- serialize graph and goals to JSON
- invoke core engine mutations directly

25.2. Callback bridge

The deep-search and goal subsystems emit events through function pointers loaded from the global registry:

- `ds_emit`
- `goal_emit`

This avoids a direct compile-time dependency from engine modules onto server internals while still letting them push live SSE updates.

25.4. Practical meaning

The HTTP layer is thin:

- it does not maintain separate business state

- it is the boundary consumed by both frontends


26. SSE event flow

The server supports multiple SSE clients, each filtered by `stream_id`.

The same client structure is reused for:

- deep-search sessions
- goal event sessions

Deep-search emits events like:

- round start
- model response
- command output
- judge outcome
- final conclusion

Goal flows emit events like:

- creation metadata
- goal started
- goal ended

This event model is how the UI surfaces long-running AI operations incrementally.


27. OpenAI transport implementation

`c/lib/openai/openai.c` is a custom HTTPS client.

It performs:

- DNS lookup with `getaddrinfo`
- socket connect
- OpenSSL TLS negotiation
- raw HTTP write/read
- response body extraction

It uses `OPENAI_API_KEY` from the environment.

There is no external OpenAI SDK in the native backend.

This matters because the project's AI dependency is deeply integrated but still low-level in transport.

30. Persistence boundaries

30.1. Graph persistence

- all nodes
- all directed connections

Node JSON includes:

- `name`
- `activation`
- `weight`
- `id`
- optional `parent`

Connection JSON includes:

- `nodes`
- `weight`

30.2. Goal persistence

- metadata

- `LoadGraphFromFile(...)`

Persistence is file-snapshot based, not transaction or DB based.


31. Technical consequences of the current design

31.1. Strengths

- Graph memory and goal memory are distinct but intentionally cross-queried.
- Deep search has a constrained command protocol instead of unconstrained tool use.
- Goal linking supports both decomposition and execution order.
- Schedule is automatically derived from behavioral state.
- OpenAI outputs are mostly schema-constrained.

31.2. Risks and constraints

- Extensive global mutable state.
- Fixed-size limits such as 1024 goals.
- Heavy use of assertions in AI-dependent flows.
- Search affects node weighting, so inspection changes the system.
- The server is concurrent, but the entire state model is not comprehensively synchronized.
- Schedule is an inference layer, not a robust planner/calendar.


32. Final technical reading of the project

From the code, CHANGE is best understood as a prototype personal cognition backend.

Its core abstractions are:

- identity as a context-partitioned semantic graph
- behavior as a hierarchical/sequential goal network
- time as a projection derived from the goal network
- investigation as an AI-controlled command loop over those structures

Everything else is wrapped around that:

- CLI starts and hosts it
- HTTP exposes it
- SSE streams its long-running operations
- `js/` visualizes graph and session state
- `react/` turns goal state into an interactive app

That is the purpose of the project and the way the `c/` contents are structurally wrapped.
